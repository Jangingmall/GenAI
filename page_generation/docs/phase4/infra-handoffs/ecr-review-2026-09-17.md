# ECR AI 이미지 구성 검토 회신 — 2026-09-17

- 검토 대상: 이창원님 「ECR AI 이미지 구성」 문서
- 회신: 생성형 AI 팀 (상세페이지 생성)

## 결론

**전체 방향은 그대로 가도 좋습니다.** 레포 분리·SHA 태그·OIDC 모두 동의합니다. 다만 **이름 규칙 한 가지는 바꾸시길 권하고**, 진행 전에 **막히는 것 세 가지**가 있습니다.

---

## 동의하는 것

| 항목 | 의견 |
| --- | --- |
| 앱별 1레포 분리 | **동의.** 서로 다른 이미지라 lifecycle·스캔 이력을 따로 두는 것이 맞습니다 |
| 태그 = 커밋 SHA 7자리, `latest` 금지, IMMUTABLE | **동의.** 되돌릴 때 어느 이미지인지 확실해집니다 |
| OIDC AssumeRole → ECR 로그인 | **동의.** 장기 키를 두지 않는 방식이 맞습니다 |
| 모델을 이미지에 굽지 않고 볼륨 마운트 | **동의하며 이미 그렇게 갑니다.** 모델은 S3 → PVC 동기화로 받고 이미지에는 런타임만 들어갑니다. 말씀대로 **이미지 = 런타임뿐이라 SHA 로 충분**합니다 |

---

## 바꾸시길 권하는 것 — 레포 이름을 엔진이 아니라 용도로

```
제안된 것                    권하는 것
jangin-ai/sglang      →     jangin-ai/page-generation
jangin-ai/ollama      →     jangin-ai/chatbot
```

`sglang`·`ollama` 는 **엔진 이름**입니다. 실제로 그 이미지가 하는 일은 상세페이지 생성과 추천 챗봇입니다.

**엔진은 바뀝니다.** 저희도 vLLM + Diffusers 로 설계했다가 SGLang 으로 옮겼습니다. 엔진이 바뀌면 레포 이름이 내용과 어긋나는데, IMMUTABLE 태그 정책상 기존 이미지를 옮길 수도 없습니다.

이미 같은 문제가 생겨 있습니다. BE 설정의 `AI_SGLANG_URL` 은 **챗봇**(Ollama 사용)을, `AI_OLLAMA_URL` 은 **상세페이지**(SGLang 사용)를 가리킵니다 — **엔진 이름이 실제와 정반대로 붙어 있습니다.** 같은 방식으로 레포 이름을 정하면 이 혼동이 ECR 까지 이어집니다.

> 이름만 바꾸면 되고 구조는 그대로입니다.

---

## 진행 전에 막히는 것 세 가지

### 1. `ollama` 이미지는 아직 만들 수 있는 주체가 없습니다

`Jangingmall/GenAI` 의 `chat_bot/` 에 **Dockerfile 이 없습니다.** 저장소 어디에도 없습니다(`page_generation/` 제외). 레포를 만들어도 올릴 이미지가 없습니다.

**챗봇 팀에 Dockerfile 작성을 요청해야 합니다.** 저희가 대신 만들 수는 있지만, 그쪽 런타임(Ollama·임베딩 모델·DB 연결)을 저희가 결정할 수는 없습니다.

덧붙여 챗봇 워크로드는 **GPU 외에 PostgreSQL + pgvector 가 필요합니다**(추천 색인). 인프라 문서에 그 항목이 없습니다. RDS 인지 클러스터 내부인지 정해야 합니다.

### 2. CI 가 아직 없습니다

`Jangingmall/GenAI` 에 **`.github` 디렉터리 자체가 없습니다.** GitHub Actions 워크플로를 **누가 작성할지** 정해야 합니다. 저희가 `page_generation` 쪽 워크플로를 쓰는 것은 가능합니다.

### 3. 이미지가 커서 표준 러너에서 빌드가 실패할 수 있습니다

SGLang 베이스(`lmsysorg/sglang:v0.5.19`)에 확산 의존성과 `bitsandbytes` 를 얹은 것만으로 **약 18~22 GB** 로 추정됩니다. 여기에 Chromium·Node·서비스 의존성이 더해집니다.

**GitHub-hosted 표준 러너는 여유 디스크가 14 GB 남짓입니다.** 빌드 도중 디스크가 찰 가능성이 높습니다. 자체 러너·큰 러너·CodeBuild 중 무엇을 쓸지 미리 정하시는 편이 좋습니다. 첫 pull 시간과 ECR 저장 비용도 함께 보셔야 합니다.

> 참고로 서비스 전용 이미지(`deploy/Dockerfile`, CPU)는 2026-09-17 에 Linux 에서 빌드해 **4.99 GB** 였습니다. **SGLang + CUDA 이미지는 아직 빌드한 적이 없어 위 수치는 추정입니다.**

## 모노레포라서 생기는 것 하나

AI 저장소는 `page_generation/` 과 `chat_bot/` 을 함께 둔 **모노레포**입니다. 커밋 SHA 는 저장소 전체의 것이므로,

- 챗봇만 바뀐 커밋에서는 상세페이지 이미지가 빌드되지 않습니다(경로 필터를 쓰면)
- 따라서 **두 레포의 SHA 태그 목록이 서로 다르고 연속적이지도 않습니다**

이게 문제는 아니지만, 배포 매니페스트에서 "같은 SHA 로 두 이미지를 맞춘다"는 가정은 성립하지 않습니다. 각 워크로드가 자기 최신 SHA 를 따로 가리키면 됩니다.

관련해서, IMMUTABLE + `latest` 금지이면 **배포 매니페스트의 이미지 태그를 올려 주는 주체**(GitOps 자동인지 수동인지)도 정해 두셔야 합니다.

## 1-1 구조에 대한 정정

인프라팀 요청서의 구조는 **맞습니다.**

```
L40S  └ ai-sglang  → page_generation (저희)
T4    └ ai-ollama  → chat_bot        (챗봇 팀)
```

앞서 저희가 **"우리는 L40S 한 장을 쓰고 Ollama 워크로드는 사용하지 않습니다"** 라고 답변드린 것이 "AI 전체에 Ollama 워크로드가 없다"는 뜻으로 읽혔을 수 있습니다. **저희 팀 범위에 없다는 뜻이었습니다.** 두 워크로드 구성이 맞고 소유 팀이 다릅니다.

- `ai-sglang` — 저희가 Dockerfile 을 작성했고 구성 정보는 [`../operations/eks-workload-spec.md`](../operations/eks-workload-spec.md) 에 있습니다
- `ai-ollama` — 챗봇 팀 소유. 위 1번 참고

각 워크로드가 FastAPI `:8000` 을 제공하는지에 대한 답은 **저희 쪽은 "예"** 입니다. 단일 컨테이너 안에서 FastAPI 가 PID 1 이고 SGLang 두 서버는 `127.0.0.1` 로만 듣습니다. 멀티컨테이너는 필요하지 않습니다.
