## 1. 사건 1: 데모 스크립트 오용

### 1) 증상

나전칠기 사진을 입력했는데 `generated/attached/najeon-023918`의 제품명이 "분홍 곡선 손잡이 부채"로 나왔다.

### 2) 증거

`scripts/runtime/generate_attached_detail_page.py`의 53~140행에는 "분홍 곡선 손잡이 부채" 프로필이 하드코딩된 렌더러 데모가 있고 `model_run: False`로 기록된다. 입력 파일의 md5·sha256은 정상이며 `model_run: false`가 실제 파이프라인이 아님을 보여 준 유일한 단서였다. 실제 파이프라인은 `run_local_detail_page.py`였다.

### 3) 원인

오케스트레이터가 파일 이름만 보고 데모 스크립트를 실제 파이프라인으로 선택했다. 이는 실행 대상을 확인하지 않은 오케스트레이터 실수이며, 관리자 오판으로 기록한다.

### 4) 조치

해당 결과를 무효로 분류하고 실제 파이프라인을 사용해 `generated/attached/najeon-real-024039`를 다시 생성했다.

### 5) 재발 방지

실행 전에 스크립트가 데모인지 실제 파이프라인인지, 하드코딩 프로필이 있는지, `model_run` 값이 무엇인지 확인하는 항목을 남겼다.

## 2. 사건 2: 모델 서버 상태 미확인

### 1) 증상

세션 재시작 사이 `mlx-serve`가 내려가 첫 꽃잎 실행이 `Connection refused`로 실패했다.

### 2) 증거

다음 명령으로 서버를 재기동했다.

```text
/Applications/MLX Core.app/Contents/MacOS/mlx-serve serve --model ~/.mlx-serve/models/ddalcu/Qwen3.8-27B-MLX-Serve-4bit --host 127.0.0.1 --port 11234
```

### 3) 원인

세션 재시작 뒤 모델 서버가 살아 있는지 확인하지 않고 실행한 오케스트레이터 실수이며, 관리자 오판으로 기록한다.

### 4) 조치

`mlx-serve`를 위 명령으로 재기동한 뒤 꽃잎 실행을 다시 진행했다.

### 5) 재발 방지

모델 실행 전 서버 프로세스와 포트 응답 상태를 확인한 뒤 작업을 시작하는 절차를 기록했다.

## 3. 사건 3: 워커 등록부 tty 불일치와 수신 확인 누락

### 1) 증상

재시작 후 터미널이 다른 tty로 떠서 rembg 배정은 agy 창으로, 라벨 제거 배정은 codex 창으로 전달되었고 두 작업 모두 실행되지 않았다. 변경 수는 0이었다.

### 2) 증거

당시 `scripts/orchestration/workers.tsv`는 codex와 agy를 서로 바꿔 가리켰고 agy2는 `missing`이었다. 사용자가 현재 작업 여부를 물었을 때 배정 직후 수신 확인을 하지 않았다는 사실이 함께 드러났다. 실제 배치는 codex `tts003`, agy `tts004`, agy2 `tts005`, codex3 `tts006`, codex2 `tts007`이었다.

### 3) 원인

등록부의 tty 상태를 최신화하지 않은 오케스트레이터 실수와, 배정 직후 워커 수신을 확인하지 않은 오케스트레이터 실수가 겹쳤다. 상태를 확인하지 않은 관리자 오판으로 기록한다.

### 4) 조치

실제 tty로 `workers.tsv`를 수정하고 작업을 다시 발행했다.

### 5) 재발 방지

재시작 뒤 워커 등록부와 실제 tty를 대조하고, 배정 직후 수신 확인을 완료한 뒤 다음 작업으로 넘어가는 절차를 기록했다.

## 4. 사건 4: uv lock 충돌과 Pillow를 올리지 않은 판단

### 1) 증상

rembg `2.0.70` 이상을 사용하려고 `uv lock`을 실행했으나 의존성 해석이 실패했다.

### 2) 증거

rembg `2.0.70` 이상은 `pillow>=12.1,<13`을 요구했지만 프로젝트는 `pillow>=10.4,<12`를 요구했다. 렌더러와 게이트는 Pillow 11에서 검증되어 있었다.

### 3) 원인

rembg의 최신 버전 요구 범위와 프로젝트 Pillow 범위가 겹치지 않았다. Pillow를 올리지 않은 판단의 근거는 렌더러와 게이트가 Pillow 11에서 이미 검증되어 있었고, rembg `2.0.69`가 Pillow를 올리지 않고 `birefnet-general`을 지원한다는 점이었다.

### 4) 조치

Pillow를 올리지 않고 rembg를 `2.0.69`로 고정했다. 최종 잠금은 rembg `2.0.69`, Pillow `11.3.0`, NumPy `2.5.3`, onnxruntime `1.29.0`이다.

### 5) 재발 방지

새 의존성을 잠그기 전에 기존 Pillow 범위와 후보 rembg 버전의 요구 범위를 함께 확인하고, 이미 검증된 런타임을 바꾸는 판단 근거를 기록한다.

## 5. 사건 5: 간헐적 `libc++abi` 종료 중단

### 1) 증상

pytest에서 `348 passed`가 출력된 직후 한 번 `libc++abi: terminating ... recursive_mutex lock failed`가 출력되었다.

### 2) 증거

재실행에서는 같은 현상이 재현되지 않았고 종료 코드는 `0`이었다.

### 3) 원인

원인은 미확인이다. onnxruntime 정리 과정이라는 추정은 있었으나 확인되지 않았다.

### 4) 조치

재실행 결과와 종료 코드를 확인했고, 원인을 확정하지 않은 채 미해결 상태로 남겼다.

### 5) 재발 방지

원인이 미확인인 상태에서는 해당 출력만으로 원인을 확정하지 않고, 재현 여부와 종료 코드를 함께 기록한다. 구체적인 원인별 예방책은 확인 필요로 남겼다.

## 6. 사건 6: 저장소 루트 부산물 파일

### 1) 증상

저장소 루트에 `:memory:.ses` 파일이 생성되어 있었다.

### 2) 증거

파일 크기는 51바이트였고 타임스탬프와 UUID가 들어 있었다. 우리 코드에서 이 파일을 만드는 경로는 확인되지 않았다.

### 3) 원인

생성 주체는 확인되지 않았다. 저장소 코드가 만드는 산출물인지 판별되지 않은 부산물이었다.

### 4) 조치

`:memory:.ses`를 삭제했다.

### 5) 재발 방지

생성 주체와 재발 방지는 확인 필요로 남겼다.

## 7. 이월 중인 미해결 사항

- `libc++abi` 중단의 원인은 미확인이다. 재실행에서는 재현되지 않았고 종료 코드는 `0`이었다.
- 합성 시도는 관리자 결정으로 반려되어 현재 코드에 남아 있지 않으며, 대조 산출물만 `generated/composite-check/{nacre,petals}`에 보존되어 있다.
- 사람 검수 점수는 존재하지 않는다.
