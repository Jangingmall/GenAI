## 1. 무엇을 만드는 시스템인가

장인이 **상품 사진 1장과 제품명·제작과정·관리법**을 올리면, 상세페이지 한 장을
만들어 낸다.

```
상품 사진 + 장인 입력
   → 비전 분석 (제품 분류·관찰·카피·레이아웃 계획)
   → 사진 구성 (누끼·생성컷)
   → 렌더 (HTML → PNG + react_document)
   → 장인 승인
   → BE 전달
```

평가 대상은 이 파이프라인 전체다.

## 3. 정성 평가

### 3-1. 평가 방식에 대한 고지

**사람 검수 점수는 수집되지 않았다.** `scripts/build_review_sheet.py` 에 검수자
사실성·심미성 항목이 정의되어 있으나 **채점된 정본이 없다.** 따라서 이 절은

- 관리자의 육안 판정 문구 (기록에 남은 원문)
- 산출물 원문 인용
- 자동 지표가 잡지 못한 관찰

으로만 구성한다. 점수를 만들어 넣지 않았다.

### 3-2. 비전 분석이 실제로 동작하는가 — 동작한다

나전칠기 보석함 사진에 맞는 힌트를 주고 돌린 결과다(2026-09-17 기록).

```
summary   나전칠기 보석함은 옻칠한 목함에 전복 자개를 오려 붙이고 ... 만든
          다단 서랍형 제품입니다.
특징      다단 서랍 구조   evidence=image-visible conf=0.95
          자개 무늬 표면   evidence=image-visible conf=0.90
          옻칠 광택 마감   evidence=image-visible conf=0.85
```

**"다단 서랍 구조" 는 힌트에 없던 정보다.** 사진에서 얻은 것이므로 비전 분석이
형태를 읽는다는 근거가 된다.

힌트를 완전히 제거하고 돌려도 같은 결론이 나온다(2026-09-21 안전성 검증 H-2).
재질을 단정하지 않고 "소재와 제작 기법은 확인이 필요합니다" 라고 쓰면서, 형태
관찰(4단 서랍·반복 곡선 문양·직사각형 외곽)은 정확했다.

### 3-3. 누끼 품질 — 관리자 육안 판정으로 채택

12차에서 기존 추출기를 rembg 로 바꿨다. 채택 근거는 62케이스 성공 수와
**관리자의 육안 판정 "잘땄네"** 다.

> 기록 원문: "관리자가 rembg 결과를 육안으로 보고 '잘땄네'라고 판정하여 rembg를
> 채택했다. 이는 사람 검수 점수가 아니라 관리자 판정 문구다."

케이스별 정량 시각 품질 점수는 존재하지 않는다.

### 3-4. 레이아웃 — 생성컷이 쓰이는가

13차 이전에는 이미지 생성을 켜도 생성된 라이프스타일 컷이 **버려졌다.** 모델이
고른 원형(`single-angle-color`)에 `usage_scene` 자리가 없었기 때문이다.

초충도 부채 세트로 전후를 비교하고 **관리자가 육안 확인 후 승인**했다.

| | 변경 전 | 변경 후 |
| --- | --- | --- |
| 고른 원형 | `single-angle-color` | `process-evidence-deep` |
| 블록 | 8개 | 10개 |
| `usage_scene` | 없음 | 있음 (`photo_id: lifestyle`) |
| 생성컷 사용 | 0장 | **5장** |
| 페이지 | 774 × 3724 | 774 × 5043 |

모델이 `process-evidence-deep` 을 고른 것은 힌트가 제작 과정을 강조했기 때문이며,
근거에 맞는 선택이다.

### 3-5. 자동 지표가 잡지 못한 것

자동 게이트가 통과시켰으나 육안·수동 확인으로 드러난 문제들이다. **평가 체계의
한계를 보여주므로 함께 남긴다.**

| 발견 | 내용 | 자동 지표 |
| --- | --- | --- |
| 힌트가 이미지를 이긴다 | 사진과 다른 재질 주장이 `image-visible` 로 표기 | 잡지 못함 |
| 상품 없는 이미지 | 순수 텍스트 이미지에 상품 설명 생성, 경고 없음 | 잡지 못함 |
| 사진 생성 실패 은폐 | 실패가 조용히 삼켜짐 (수정 완료) | 잡지 못함 |
| `page_plan` 의 없는 사진 참조 | `photo_id: scale` 이 `photos` 에 없음 (수정 완료) | 잡지 못함 |

## 4. 비교표

### 4-1. 누끼 추출기 — 기존 방식 vs rembg (62케이스)

| 항목 | 기존 추출기 | **rembg `birefnet-general`** |
| --- | --- | --- |
| 누끼 성공 | **11/62건** | **62/62건** |
| 실행률 (60건 기준) | 15.0% (9성공 / 51폴백) | — |
| 주요 실패 사유 | `CORNER_NON_UNIFORM` 50건 | — |
| 모서리 편차 중앙값 | 101.3 (임계값 24) | — |
| 반투명 전경 보존 | 한계 있음 | 개선 |
| 채택 | — | **채택** (관리자 육안 판정) |

기존 추출기는 **모서리 밝기 균일성**으로 배경을 판정했다. 미술관 사진처럼 배경이
균일하지 않으면 통과하지 못해 60건 중 51건이 폴백했다. rembg 는 학습 기반이라 이
제약이 없다.

**대가**: rembg 는 CPU 에서 프로세스당 약 **12.9 GiB** 를 점유하고 누끼 1장에
25~30초(8코어) 걸린다. 그래서 배포 이미지는 `onnxruntime-gpu` 로 전환했다(미검증).

### 4-2. 다양성 기준 — 13차 정정 전후

| 항목 | 정정 전 | **정정 후** |
| --- | --- | --- |
| 귀무모형 추출 | 비복원 | **복원** (실제 파이프라인과 일치) |
| 시뮬레이션 크기 | `min(N, 25)` 로 잘림 | **실제 N** |
| 완전 일치 쌍 기준 | 고정 1쌍 | **배치 크기의 p95** |
| 평균 일치도 기준 | 평균 + 고정 10.0%p | **p95 + 검증 패딩 1.0%p** |
| N=6 기준값 | 66.4% | 66.0% (사실상 동일) |
| N=60 기준값 | 66.3% | **59.0%** |
| 60건 실측 판정 | 완전 일치 쌍 미달 | **평균 일치도 미달** |

정정 전 기준은 **N=6 에서 유도된 값**이라 소규모 파일럿에만 맞았다. 60건에서는
완전 일치 쌍 기준이 구조적으로 통과 불가였고(기대값 자체가 0), 평균 일치도 기준은
반대로 7%p 넘게 느슨했다. **양쪽 다 바로잡은 결과 통과·미달이 서로 뒤바뀌었다.**
