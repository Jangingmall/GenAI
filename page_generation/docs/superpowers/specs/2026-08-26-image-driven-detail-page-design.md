# 이미지 기반 상품 상세페이지 생성 시스템 설계 (보관용 초기안)

> 이 문서는 초기 생성형 최종 이미지 설계를 보관한 문서입니다. 현재 운영 기준은
> [원본 보존형 설계](2026-08-27-source-preserving-detail-page-design.md)이며, 제품 전체를
> Gemini/Bedrock image-to-image로 재생성하지 않습니다.

> 2026-09-08 최신화 메모: 이 보관용 초기 설계는 최종 이미지 생성 중심의 과거안이다. 현재
> FE에는 실행 가능한 HTML 대신 `react_document` 제한형 JSON AST를 전달하고, 승인 후 내부
> HTML/CSS renderer로 PNG를 만든다. `page_plan`은 모델·편집·하위 호환 DTO로 남아 있으며,
> 현재 계약은 [AI DTO 계약](../../api/ai-dto-contract.md)을 우선한다.
> 이 문서의 직접 FE→AI 흐름과 생성형 최종 이미지 설명은 이력으로만 읽고, 현재 운영 경계는
> `FE → 상품 BE → AI → 상품 BE → FE`로 해석한다.

## 1. 목표

상품 이미지 한 장을 입력받아 AI가 이미지에서 확인 가능한 상품 특징을 스스로 분석하고, 참고용 상세페이지 템플릿의 구성과 분위기를 반영한 긴 세로형 상세페이지 이미지 한 장을 생성한다. 생성된 상품 정보와 상세페이지 이미지는 백엔드 API로 전달해 DB에 적재한다.

백엔드가 사전에 상품 설명을 제공하는 구조가 아니다. 상품 이미지가 상품 정보의 주된 근거이며, 이미지에서 확인할 수 없는 성능·수치·인증·효능·정확한 소재 등의 정보는 만들어내지 않는다.

## 2. 범위

포함:

- 이미지 파일 검증 및 MIME 타입 확인
- 이미지 기반 상품 특징·카피·섹션 계획 분석
- 분석 결과를 구조화된 상품 프로필로 정규화
- 원본 상품 이미지와 참고 템플릿을 이용한 긴 세로형 상세페이지 이미지 생성
- 생성된 상품 프로필 및 결과 이미지의 백엔드 전송
- 실패 시 재시도 가능한 오류와 로컬 결과 보존
- 외부 API를 호출하지 않는 단위 테스트

제외:

- 상품 이미지 촬영·보정
- 가격, 재고, 배송, 주문 기능
- DB 스키마와 ORM 구현
- 이미지 저장소(오브젝트 스토리지) 운영

## 3. 권장 아키텍처

```text
입력 이미지
    ↓
ImageValidator
    ↓
VisionAnalyzer ──→ ProductProfile(JSON)
    ↓                       ↓
    └──────────────→ DetailPageRenderer
                            ↓
                 generated_detail_page.png
                   ↙                    ↘
             AI-FE 전달             AI-BE 전달
                 ↓                      ↓
              FE 표시                BE DB 적재
```

### 3.1 1차 분석

비전 모델이 원본 이미지를 분석해 내부용 `ProductProfile`을 만든다. 분석 프롬프트는 다음을 요구한다.

- 제품 종류, 형태, 색상, 구성, 시각적으로 확인되는 질감
- 이미지에서 직접 확인되는 차별점
- 과장하지 않은 짧은 한국어 핵심 문구
- 제품을 자연스럽게 보여줄 수 있는 사용 장면
- 확실하지 않거나 이미지로 확인할 수 없는 정보 목록

결과는 엄격한 JSON으로 받고, 애플리케이션에서 필수 필드·문자열 길이·배열 길이를 검증한다. 분석 결과는 사용자에게 직접 노출하지 않고 최종 이미지 생성의 입력으로만 사용한다.

### 3.2 2차 이미지 생성

이미지 생성 모델에 다음을 함께 전달한다.

- 원본 상품 이미지
- 저장소의 참고 템플릿 이미지
- 검증된 `ProductProfile`
- 상세페이지 레이아웃·카피·사실성 규칙

최종 출력은 설명이나 여러 파일이 아닌 이미지 한 장이다. 참고 템플릿은 레이아웃과 여백의 참고로만 사용하고, 템플릿 안의 자리표시자 문구는 복사하지 않는다.

Gemini 3.1 Flash Image의 `1:4` 비율과 `2K` 출력을 기본값으로 사용한다. 참고 파일의 실제 비율은 약 `1:4.18`이므로, API 출력은 `1:4`로 생성하고 정확한 최종 크기 정규화는 후속 요구사항으로 분리한다.

## 4. 모듈 경계

### `image_validator`

입력 파일이 지원 MIME 타입인지, 비어 있지 않은지, 최대 크기를 넘지 않는지 검증한다.

### `vision_analyzer`

이미지와 분석 프롬프트를 Gemini에 전달하고 `ProductProfile`을 반환한다. 모델 호출 세부사항은 이 모듈 안에 감춰서 테스트에서 가짜 분석기로 교체할 수 있게 한다.

### `detail_page_renderer`

원본 이미지·템플릿·`ProductProfile`을 받아 이미지 생성 모델을 호출하고 생성 이미지 바이트를 반환한다. 출력 이미지가 실제로 존재하는지 확인한다.

### `ai_be_client`

생성된 상품 프로필과 이미지 파일을 백엔드의 configurable HTTP endpoint로 전송한다. URL, 인증 토큰, 타임아웃은 환경변수로 설정한다. 중복 적재 방지를 위해 `generation_id`와 idempotency key를 전달한다. 이 채널은 FE에 반환하는 DTO와 분리한다.

### `ai_fe_delivery`

FE가 표시할 작업 상태, 생성된 상품 요약, 상세페이지 이미지 결과를 AI-FE DTO로 반환한다. AI-FE 전달 실패가 AI-BE 재시도를 막지 않도록 두 채널을 독립적으로 처리한다.

### `pipeline`

전체 순서를 조정한다. 분석 성공 전에는 이미지 생성을 호출하지 않고, 이미지 생성 성공 전에는 백엔드 적재를 호출하지 않는다. 백엔드 적재 실패 시 생성 결과를 폐기하지 않고 재전송 가능한 결과 객체를 반환한다.

## 5. 데이터 계약

FE/BE/AI 간 공개·내부 API의 요청 및 응답 DTO, 상태 값, 오류 코드, DB 적재 기준은 별도 계약 문서에서 관리한다.

- [FE/BE/AI DTO 입출력 계약](../../ai-dto-contract.md)

### 5.1 내부 `ProductProfile`

`ProductProfile`은 분석 관찰값과 생성 카피를 구분해 보존한다. 구체적인 필드명과 예시는 [FE/BE/AI DTO 입출력 계약](../../ai-dto-contract.md)의 `product` 객체를 기준으로 한다.

- `observations`: 이미지에서 직접 관찰한 색상·형태·구성·질감
- `features`: 관찰값에 근거한 제품 특징과 confidence
- `copy_sections`: 상세페이지에 표시할 짧은 한국어 카피
- `uncertain_information`: 이미지로 확인할 수 없는 정보
- `safety_notes`: 과장 표현 방지를 위한 주의사항

### 5.2 백엔드 전송

기본 연동은 `multipart/form-data`로 정의한다.

- `metadata`: JSON 문자열
- `detail_page_image`: 생성된 PNG/JPEG 바이너리

`metadata` 예시:

```json
{
  "request_id": "uuid",
  "product": {},
  "source_image_mime_type": "image/png",
  "generated_image_mime_type": "image/png",
  "generation": {
    "model": "gemini-3.1-flash-image",
    "aspect_ratio": "1:4",
    "image_size": "2K",
    "prompt_version": "detail-page-v1"
  }
}
```

백엔드 URL·인증 헤더명·필드명은 환경변수로 바꿀 수 있게 한다. BE가 AI 응답을 저장소 URL로 변환하고 DB에 적재하는 책임을 갖는다. 실제 백엔드가 이미지 바이너리를 받지 않고 저장소 URL만 받는 경우에는 AI 응답의 asset 전달 방식만 교체한다.

FE가 AI에 작업을 접수하고 결과를 조회하는 AI-FE API 및 AI가 BE에 생성 결과를 적재하는 AI-BE 내부 multipart 계약은 [AI-FE / AI-BE DTO 입출력 계약](../../ai-dto-contract.md)을 따른다.

## 6. 프롬프트 정책

분석 프롬프트와 이미지 생성 프롬프트는 별도 파일 또는 상수로 관리하고 버전을 포함한다.

공통 정책:

- 입력 이미지 속 제품의 정체성, 색상, 비율, 형태를 유지한다.
- 이미지에서 읽을 수 없는 스펙과 효능을 사실처럼 표현하지 않는다.
- 숫자, 인증, 원산지, 소재명, 성능 수치를 임의로 추가하지 않는다.
- 짧고 읽기 쉬운 한국어 문구를 사용한다.
- 제품이 여러 개로 복제되거나 다른 제품으로 변형되지 않게 한다.
- 최종 응답은 긴 세로형 상세페이지 이미지 한 장으로 제한한다.

## 7. 오류 처리

- 잘못된 이미지: 입력 검증 오류로 즉시 종료
- 상품을 식별하기 어려움: 분석 결과에 불확실성을 기록하고 보수적인 카피로 진행하거나 명시적인 분석 오류 반환
- 분석 JSON 파싱 실패: 제한 횟수 내 재시도 후 분석 오류 반환
- 이미지 생성 실패 또는 이미지 블록 누락: 생성 오류 반환
- 백엔드 전송 실패: 생성된 이미지와 프로필을 로컬 결과로 보존하고 재시도 가능한 전송 오류 반환
- 모든 외부 호출에는 제한 시간과 명확한 오류 메시지를 적용

## 8. 검증 기준

- 이미지 한 장만으로 `ProductProfile`이 생성된다.
- 분석 결과가 JSON 계약을 항상 만족한다.
- 최종 이미지가 한 개의 세로형 파일로 반환된다.
- 원본 이미지에 없는 확정적 상품 주장이 프롬프트에 포함되지 않는다.
- 가짜 Gemini 응답으로 파이프라인의 성공·실패 경로를 테스트할 수 있다.
- 가짜 백엔드 클라이언트로 전송 payload와 호출 순서를 검증할 수 있다.
- 백엔드 실패 뒤에도 재시도에 필요한 결과가 반환된다.

## 9. 운영 설정

```text
GEMINI_API_KEY=...
GEMINI_ANALYSIS_MODEL=...
GEMINI_IMAGE_MODEL=gemini-3.1-flash-image
BACKEND_PRODUCT_URL=...
BACKEND_AUTH_TOKEN=...
BACKEND_TIMEOUT_SECONDS=60
DETAIL_PAGE_TEMPLATE_PATH=상세페이지 템플릿 이미지 경로
```

API 키와 인증 토큰은 코드나 저장소에 기록하지 않는다.
