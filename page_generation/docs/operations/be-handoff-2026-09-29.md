## 1. 승인 재요청 — 409 "Approval is already in progress"

### 무엇이 바뀌었나

`POST /internal/v1/ai/detail-page-renders`(승인)는 렌더에 **수 분**이 걸립니다.
이전에는 렌더하는 동안 AI 서버 전체가 다른 요청에 응답하지 못했습니다. 이제는 렌더 중에도 상태 조회 등이 정상 응답합니다.

그 대신 **렌더가 진행 중일 때 같은 승인을 다시 보내면** 아래 응답이 옵니다.

```
HTTP 409
{"detail": "Approval is already in progress"}
```

| 상황 | 이전 | 이후 |
| --- | --- | --- |
| 렌더 중 같은 승인 재요청 | 첫 렌더가 끝날 때까지 응답이 지연된 뒤 200 | **즉시 409** "Approval is already in progress" |
| 렌더 완료 후 같은 승인 재요청 | 200 (저장된 결과) | 200 (저장된 결과) — 같음 |
| 같은 멱등키에 다른 내용 | 409 "Idempotency key conflict" | 409 "Idempotency key conflict" — 같음 |

### BE 에서는 평소 흐름에 영향이 없습니다

BE 코드를 확인해 보니 `RestAiContentClient.approveRender` 는 승인을 **재시도 없이 한 번만** 보냅니다.
그래서 이 409 는 **BE 가 같은 승인을 다시 보낼 때만** 나오고, 지금 흐름에서는 받을 일이 없습니다.
나중에 재시도를 넣으신다면, 이 409 는 실패가 아니라 "잠시 뒤 다시 보내면 완료 결과를 받는다"는 뜻입니다.
같은 409 라도 `"Idempotency key conflict"` 는 진짜 충돌이니 **`detail` 로 구분**해 주세요.

### 대신 확인이 필요한 것 — 승인 호출 타임아웃 300초

`application-prod.yml` 의 `ai.timeout-seconds` 가 **300초**이고, 승인 호출에도 이 값이 그대로 걸립니다.

- 승인 호출은 **렌더가 끝나야** 응답이 돌아옵니다(사진 생성 + 페이지 캡처)
- **L40S 에서의 렌더 시간은 아직 측정하지 못했습니다.** 로컬(Apple Silicon) 기준 분석+렌더 전체가 평균 254초였습니다
- 렌더가 300초를 넘으면 BE 쪽 호출은 타임아웃 예외로 끝나지만, **AI 는 렌더를 계속해서 콜백으로 `COMPLETED` 를 보냅니다.**
  BE 가 이 타임아웃 예외를 받았을 때 generation 을 어떻게 처리하는지 확인해 주세요. 실패로 표시하더라도
  이후 도착하는 콜백이 `COMPLETED` 로 덮어쓰는지(`complete()` 에 상태 제한이 없어 덮어쓸 것으로 보입니다)도 함께 봐 주세요
- 참고로 `.env.example` 의 `AI_TIMEOUT_SECONDS=30` 은 `application-local.yml` 에서만 쓰입니다. 로컬에서 이 값을 그대로 쓰면
  승인이 30초 만에 타임아웃됩니다. 운영(`application-prod.yml`)은 300 고정이라 영향이 없습니다

GPU 에서 렌더 시간을 측정하면 이 값이 충분한지 알려 드리겠습니다.

## 2. 콜백 재시도 규칙

### 무엇이 바뀌었나

AI 가 `POST {BACKEND_URL}/internal/generations/{generation_id}/completion` 으로 결과를 보낼 때,
BE 응답에 따라 재시도 여부를 정합니다. 이번에 **재시도하면 안 되는 응답까지 재시도하던 문제**를 고쳤습니다.

| BE 응답 | AI 동작 |
| --- | --- |
| 2xx (`SAVED`, `ALREADY_SAVED` 모두) | 전달 완료 |
| 409 | 이미 저장됨으로 보고 전달 완료 |
| 5xx, 429 | 재시도 |
| 네트워크 오류·타임아웃 | 재시도 |
| **그 외 4xx** (400·401·403·404·413·422 등) | **재시도 안 함 — 영구 실패로 기록** |

재시도는 **최대 8회**, 간격은 1초부터 두 배씩 늘어 최대 300초입니다.

| | 이전 | 이후 |
| --- | --- | --- |
| 4xx (409·429 제외) | 8회까지 재시도, **재시작할 때마다 다시 시도** | **즉시 중단** |
| 8회를 넘긴 실패 | **재시작·재처리 때마다 계속 다시 보냄** | 더 이상 보내지 않음 |

### BE 에 부탁드리는 것

**일시적인 문제는 5xx 또는 429 로 응답해 주세요.** 예를 들어 DB 가 잠깐 바쁘거나 S3 업로드가 일시적으로
실패한 경우를 4xx 로 응답하면, AI 는 영구 실패로 보고 다시 보내지 않습니다.

`completeWithImages` 에서 generation 을 못 찾으면 `NotFoundException` 이 납니다. 이게 **404** 로 나간다면
AI 는 재시도하지 않습니다. generation 이 **아직 커밋되기 전**에 콜백이 도착하는 경우가 있을 수 있다면 알려 주세요.

## 3. 같은 결과가 두 번 콜백되는 경우 — BE 가 이미 막고 있습니다

AI 서버가 **렌더 도중 재시작되면**, 그 승인을 "진행 중"에서 풀어 BE 가 다시 요청할 수 있게 했습니다.
첫 시도가 **BE 콜백까지 마친 직후** 재시작됐다면 같은 결과가 한 번 더 콜백됩니다.

BE 코드를 확인해 보니 **이미 막혀 있습니다.**

- AI 는 콜백의 멱등키로 **`generation_id` 를 그대로** 보냅니다
- BE `GenerationService.completeWithImages` 는 그 멱등키로 기존 generation 을 찾아 **`COMPLETED` 면 저장하지 않고
  200 `ALREADY_SAVED`** 를 돌려줍니다
- AI 는 `ALREADY_SAVED` 를 전달 완료로 처리합니다

**BE 조치는 필요 없습니다.** 이 경우 BE 에는 **첫 번째 렌더 결과**가 남습니다.

## 4. BE-11 — 승인·콜백 시점

### 문제였던 것 (9/22 요청)

BE 는 작업 제출 후 **31분(1861초)** 안에 콜백이 오지 않으면 generation 을 `FAILED` 로 바꿨습니다.
그런데 AI 는 장인이 초안을 **승인한 뒤에야** 렌더하고 콜백합니다.

```
작업 접수(202) → 분석(약 4분) → DRAFT_READY ← 장인 검토·수정 (시간 제한 없어야 함)
                                        ↓ 승인
                                  렌더 → 콜백 → COMPLETED
```

그래서 **장인이 초안을 31분 넘게 보면 정상 작업이 `FAILED` 로 찍히는** 문제가 있었고, 세 가지 방안을 드렸습니다.

| 방안 | 내용 | 결과 |
| --- | --- | --- |
| A | 초안 시점에 BE 가 알 수 있게 하고, 승인은 BE·FE 에서 | 데드라인이 기계 시간에만 걸림. 장인 검토 시간 제한 없음 |
| B | 승인 단계 제거 (초안 = 최종) | 장인이 초안을 못 고침 — 제품 결정 필요 |
| C | 현행 유지 + 데드라인 연장 | 데드라인이 AI 장애 감지 역할을 못 함 |

### BE 9/28 변경으로 풀린 것으로 보입니다

BE 커밋 `d48f6a0`(PR #76, 2026-09-28)의 `GenerationDeadlineScheduler` 를 확인했습니다.

| 동작 | BE 코드 |
| --- | --- |
| 60초마다 `QUEUED` generation 의 AI 작업 상태를 조회 | `pollQueuedGenerations` → `GET /internal/v1/ai/detail-page-jobs/{jobId}` 의 `status` |
| AI 가 `DRAFT_READY` 면 generation 을 **`DRAFT_READY` 로 전이** | `applyDraftReady` → `markDraftReady()` |
| AI 가 `FAILED` 면 generation 을 `FAILED` 로 | `applyFailed` |
| 31분 데드라인은 **`QUEUED` 인 것에만** 적용 | `findAllByStatusAndRequestedAtBefore(QUEUED, deadline)` |
| `DRAFT_READY` 에서 완료 콜백을 받아 `COMPLETED` 로 | `complete()` 에 상태 제한 없음 |

AI 쪽도 맞물립니다. 상태 조회 응답의 `status` 에 `DRAFT_READY` 가 나옵니다.

```
작업 접수 → QUEUED ──(BE 폴링, 최대 60초)──→ DRAFT_READY  ← 데드라인 대상에서 빠짐
                                                  ↓ 장인 승인 (시간 제한 없음)
                                            렌더 → 콜백 → COMPLETED
```

결과적으로 **A 방안과 같은 효과**(데드라인은 AI 분석 시간에만 걸리고 장인 검토 시간은 제한 없음)를
**AI 쪽 변경 없이** 얻었습니다. 저희가 A 에서 하겠다고 했던 "콜백 시점 이동"은 **필요 없어졌습니다.**

### 확인 부탁드리는 것

- 이 폴링 방식이 **BE-11 의 확정 결정**인지 알려 주세요. 확정이면 저희는 콜백 시점을 옮기지 않고 현재 흐름을 유지합니다
- 코드로만 확인했습니다. **Stage 연동 테스트로** "분석 완료 → BE `DRAFT_READY` → 31분 경과 후에도 유지 → 승인 → `COMPLETED`"를
  한 번 확인했으면 합니다
- 폴링이 AI 상태를 못 읽으면(내부 토큰 오류 등) 로그만 남기고 넘어가서, 결국 31분 뒤 `FAILED` 가 됩니다.
  이 경우는 데드라인 본래 목적(AI 연결 장애 감지)대로 동작하는 것이라 문제는 아니지만, **토큰 설정을 연동 테스트 때 같이 봐야** 합니다

## 5. BE 조치 없이 좋아지는 것

| 내용 | 효과 |
| --- | --- |
| 승인 렌더가 다른 요청을 막지 않음 | 렌더 중에도 **BE 폴링의 상태 조회**·초안 저장·헬스 체크가 정상 응답 |
| 같은 멱등키로 동시에 작업을 만들어도 1개만 생성 | 중복 작업 방지 (기존 계약과 같음, 보장이 강해짐) |
| 첫 콜백이 일시적으로 실패하면 재시도 예약 | 이전에는 재시도가 예약되지 않고 다음 재처리 때까지 대기했음 |

1절의 409 를 빼면 **API 요청·응답 형식은 바뀌지 않았습니다.**
