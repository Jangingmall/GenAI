# 깃허브 협업 규칙

> 미담 AI 추천 챗봇 · 2인 협업 기준.
> 브랜치·커밋·PR 등 깃허브 워크플로우 규칙. (코드 작성 규칙은 `CODE_STYLE.md` 참고)
> 규칙은 "딱 필요한 만큼"을 지향한다 — 개발을 느리게 하지 않으면서 충돌·혼선만 막는다.

---

## 1. 브랜치 전략

```
main                     ← 항상 돌아가는 안정 코드 (직접 커밋 금지)
 ├─ feat/<설명>           ← 새 기능 작업
 ├─ fix/<설명>            ← 버그 수정
 └─ docs/<설명>           ← 문서 작업
```

### 규칙
- **main에 직접 커밋하지 않는다.** 반드시 브랜치를 만들어 작업하고 PR로 병합한다.
- main에는 **실서비스 가능한 수준의 안정 코드**만 둔다. 실험·미완성 코드는 브랜치에서.
- 브랜치는 **작업 단위로 짧게** 만든다. 하나의 브랜치가 여러 기능을 담지 않는다.
- 병합이 끝난 브랜치는 **삭제**한다.

### 브랜치명 규칙
`<종류>/<간단한-설명>` (소문자, 하이픈 구분)

| 종류 | 용도 | 예시 |
| :--- | :--- | :--- |
| `feat/` | 새 기능 | `feat/vector-search`, `feat/intent-extraction` |
| `fix/` | 버그 수정 | `fix/rrf-bug`, `fix/embedding-dim` |
| `docs/` | 문서 | `docs/api-spec` |
| `refactor/` | 리팩터링 | `refactor/ranking-module` |

---

## 2. 커밋 규칙

### 커밋 메시지 형식
`<종류>: <한 줄 요약>`

```
feat: 벡터 검색 기본 구현
fix: 유사도 컷 임계값 오류 수정
docs: README 세팅 방법 추가
refactor: 랭킹 로직 함수 분리
test: 인젝션 방어 평가셋 추가
chore: requirements 업데이트
```

### 종류(prefix)
| 종류 | 언제 |
| :--- | :--- |
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 |
| `refactor` | 기능 변화 없는 코드 개선 |
| `test` | 테스트·평가셋 |
| `chore` | 설정·의존성 등 잡일 |

### 커밋 습관
- **자주, 작게 커밋한다.** 하루치를 몰아 한 번에 커밋하지 않는다 — 충돌이 적고 되돌리기 쉽다.
- 커밋 하나 = 의미 있는 변경 하나.
- 요약은 한국어로 써도 된다. 팀에서 한/영 통일.

---

## 3. Pull Request (병합)

- 작업이 끝나면 브랜치를 push하고 **Pull Request**를 올린다.
- **상대방이 한 번 리뷰하고 병합**하는 것을 원칙으로 한다 (서로 코드를 알게 됨).
- 단, 사소하거나 급한 변경은 **셀프 병합을 허용**한다 (서로 대기하지 않기 위함).
- PR 제목도 커밋과 같은 형식(`종류: 요약`)을 권장.
- PR 설명에 **무엇을·왜** 바꿨는지 간단히 적는다.

### 병합 전 필수 — 최신 main 반영
작업 브랜치가 오래되면 main과 벌어져 충돌이 커진다. 병합 전 최신을 맞춘다:
```bash
git checkout main
git pull origin main
git checkout <내-브랜치>
git merge main          # 충돌 있으면 여기서 해소
```

> 분업이 파일 단위로 나뉘어 있어(예: `search.py`는 A, `generate.py`는 B) PR이 겹칠 일이 적다. 자기 영역은 빠르게 병합해도 된다.

---

## 4. 커밋 금지 사항

- **`.env`를 커밋하지 않는다.** (비밀번호 노출 방지 — `.gitignore`에 포함됨)
- 가상환경(`.venv/`), 모델 캐시, 대용량 파일을 커밋하지 않는다. (`.gitignore` 확인)
- 비밀번호·API 키를 코드나 커밋에 포함하지 않는다.

---

## 5. 작업 흐름 요약

```
1. git checkout main && git pull origin main   # 최신 받기
2. git checkout -b feat/새기능                   # 브랜치 생성
3. (작업 + 자주 커밋: "feat: ...")
4. git merge main                               # 병합 전 최신 반영
5. git push origin feat/새기능                   # 푸시
6. GitHub에서 PR 생성 → (상대 리뷰) → 병합
7. 병합된 브랜치 삭제
```

### 체크리스트
- [ ] main 최신을 받고 새 브랜치를 만들었는가
- [ ] 브랜치명이 `종류/설명` 형식인가
- [ ] 커밋 메시지가 `종류: 요약` 형식인가
- [ ] `.env`·대용량 파일이 포함되지 않았는가
- [ ] 병합 전 최신 main을 반영했는가
- [ ] PR을 올렸는가
