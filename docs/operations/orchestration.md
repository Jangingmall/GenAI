# 멀티 에이전트 오케스트레이션 운영 규약

cmux 워크스페이스 하나에서 여러 CLI 에이전트를 동시에 굴리기 위한 규약이다.
지휘자(오케스트레이터)는 Claude Code 세션 하나이며, 나머지 터미널은 워커다.

## 역할

| 역할 | 터미널 제목 | 에이전트 |
| --- | --- | --- |
| 오케스트레이터 | `◐ 오케스트레이션 세팅` | Claude Code (Opus 5) |
| 워커 `codex` | `Team3_EcommerceSystemAI` | OpenAI Codex CLI |
| 워커 `agy` | `agy` | Antigravity CLI (Gemini) |

워커는 `scripts/orchestration/workers.tsv` 에 등록한다. 서피스 UUID 는 앱을 다시 띄우면
바뀌고, 터미널 **제목은 CLI 가 자기 실행 명령으로 갈아치우기 때문에**(예: agy 를 재기동하면
제목이 `agy --dangerously-skip-permissions` 로 바뀐다) 식별자로 쓸 수 없다. 그래서 pane 수명
동안 고정되는 **tty 로 해석**한다. 워커를 추가/변경하려면 `cmux tree --all` 에서 tty 를 확인해
`alias<TAB>tty<TAB>종류<TAB>idle_정규식` 한 줄을 넣는다.

## 작업 배정 기준 (2026-09-10 측정)

브리프 36건의 발행·완료 시각과 재작업 발생 여부를 집계한 결과다. 재작업은 **후속 수정
브리프가 실제로 발행된 건**만 센다.

| 워커 | 배정 | 재작업 | 재작업률 | 중앙 소요 | 최장 | 완주 실패 |
|---|---:|---:|---:|---:|---:|---|
| agy | 14 | 3 | 21% | 2.8분 | 32.9분 | 0 |
| codex | 11 | 2 | 18% | 6.3분 | 31.1분 | 0 |
| agy2 | 6 | 0 | 0% | 2.6분 | 32.7분 | 0 |
| codex2 | 5 | 0 | 0% | 6.7분 | 33.3분 | **2 (40%)** |

**재작업률만 보고 비교하면 안 된다.** 두 계열이 맡은 작업의 성격이 다르다. 재작업의 내용을
보면 갈라진다.

- **agy 재작업 3건은 전부 판정 로직의 정확성** — 파이프라인에 없는 인자를 넘겨 6건 전건 실패,
  보존율을 캔버스 기준으로 재서 정상 산출물을 오탐, 오분류를 감지하고도 종료 코드 0 반환.
  전부 "돌아는 가는데 틀린 답을 내는" 유형이다.
- **codex 재작업 2건은 자기 산출물의 일관성** — 재조직 후 하위 호환 심볼릭 링크를 남기면서
  그 경로의 부재를 요구하는 테스트를 같이 넣었고, 마스크 1차 수정이 그림자 잔재를 남겼다.
  둘 다 검수에서 잡혔고 지적 후 한 번에 고쳤다.
- **codex2 는 5건 중 2건이 완주하지 못했다** — 1건은 샌드박스가 localhost 를 막아 모델 서버에
  닿지 못했고(환경 제약), 1건은 설계안을 제시하고 승인을 기다리며 33분간 멈춰 있었다.
  품질 문제가 아니라 자율성 문제다.

### 배정

| 티어 | 워커 | 맡는 것 |
|---|---|---|
| `core` | **codex + agy** | 핵심 로직, 근본 원인 진단, 테스트 동반 수정. **둘이 교차검증한다.** |
| `build` | agy2, codex3 | 도구·스크립트·문서 생성. codex3 는 `luna max` 라 무거운 건을 맡는다. |
| `chore` | codex2 | 반복 실행, 감시, 지표 도구 |
| 최종 검수 | 오케스트레이터 | 모든 산출물의 수용 판정 |

### core 교차검증 절차

핵심 작업은 codex 와 agy **양쪽에 같은 브리프를 병렬로 발행**하고, 두 결과를 대조한 뒤
차이 나는 지점만 오케스트레이터가 판정한다. 순차로 돌려 뒤쪽이 앞쪽을 보게 하면 교차검증이
아니라 추인이 된다. 브리프에 **상대 결과를 찾아보지 말라**고 명시한다.

이 방식이 값어치 있는 근거는 측정에 있다. AI 검수를 두 모델에 독립으로 돌렸을 때
codex 는 6건 중 5건을 4/4/4/4 로 매겨 변별력이 없었고, agy 는 2~5 로 갈랐다. 반대로
`steps`·`strength` 유실의 소스 레벨 원인은 codex 만 찾아냈다. **둘의 강점이 겹치지 않으므로
한쪽만 쓰면 그쪽의 사각이 그대로 결과가 된다.**

대조에서 갈리는 지점은 세 가지로 처리한다.

1. **양쪽이 같은 결론** — 그대로 채택한다.
2. **한쪽만 발견** — 발견한 쪽의 근거를 오케스트레이터가 코드나 산출물로 직접 검증한 뒤 채택한다.
   실제로 codex 만 제기한 '참고용 표시 누락'은 검증 결과 사실이었고, agy 는 놓쳤다.
3. **결론이 상반** — 어느 쪽도 채택하지 않고 오케스트레이터가 판정한다.

병렬 발행이 GPU·파일을 동시에 건드리는 작업이면 교차검증을 쓰지 않는다. 한쪽에만 맡기고
결과를 다른 쪽에 검토시키는 순차 방식으로 바꾼다.

### codex2 를 chore 로 쓸 때의 제약

**codex 샌드박스는 localhost 를 막는다.** 측정에서 codex2 에 파일럿 재실행을 맡겼을 때
`curl http://127.0.0.1:11234/v1/models` 가 exit 7 로 실패해 작업을 시작조차 못 했다.
반복 실행 중 상당수가 모델 서버를 호출하므로, 그대로 두면 chore 티어가 성립하지 않는다.

2026-09-10 재기동으로 해소했다. 띄우는 명령은 다음과 같다.

```
codex --dangerously-bypass-approvals-and-sandbox
```

**재기동 후 네트워크가 실제로 열렸는지는 첫 서버 호출 작업에서 확인한다.** chore 브리프의
1단계를 항상 모델 서버 확인으로 두고, exit 7 이 나오면 중단하고 보고하게 한다.

### 브리프 작성 규칙 (재작업 5건에서 나온 것)

- **합격 기준을 수치로 박는다.** agy 재작업 3건은 전부 "무엇이 맞는지"가 브리프에 없었다.
  지표 재설계 때 정답을 아는 검증 사례 두 개(지워진 산출물은 심각 손실, 온전한 산출물은 OK)를
  주었더니 한 번에 정확히 나왔다.
- **codex 에 모델 서버 호출 작업을 주지 않는다.** 샌드박스가 localhost 를 막아 `curl` 이 exit 7 로 실패한다.
- **codex2 에는 승인 대기 금지를 명시한다.** 설계 확인을 기다리며 멈추는 경향이 있다.
- **동시 작업 중인 파일을 브리프에 적어 준다.** 실행 중이던 렌더 스크립트가 다른 워커의
  디렉터리 재조직으로 옮겨져 파일럿 2건이 죽었다.

## 지휘 도구

```
scripts/orchestration/orc list                 # 워커와 idle/busy 상태
scripts/orchestration/orc send <alias> "…"     # 한 줄 지시
scripts/orchestration/orc task <alias> "제목"  # stdin 브리프를 파일로 넘김 (긴 작업)
scripts/orchestration/orc wait <alias> [sec]   # 입력 대기 상태로 돌아올 때까지 폴링
scripts/orchestration/orc read <alias> [lines] # 워커 화면 회수
scripts/orchestration/orc board                # 작업 보드
```

## 배분 규칙

1. **긴 지시는 `orc send` 로 보내지 않는다.** TUI 프롬프트는 개행에서 바로 제출되므로
   두 줄 이상이면 `orc task` 로 브리프 파일(`.orchestration/tasks/<시각>-<alias>.md`)을
   만들고, 워커에게는 "그 파일을 읽고 수행하라"는 한 줄만 보낸다.
2. **파일 충돌을 방지한다.** 같은 파일을 두 워커에 동시에 배정하지 않는다. 브리프에
   담당 경로를 명시하고, 겹치면 순차로 돌린다.
3. **워커는 자기 브리프 파일 하단에 `## 결과` 로 보고**한다. 지휘자는 `orc wait` 후
   브리프 파일과 `git diff` 로 검증한다. 화면(`orc read`)은 보조 확인용이다.
4. **커밋은 지휘자만 한다.** 워커에게는 커밋·푸시·서버 실행을 시키지 않는다.
5. `.orchestration/` 은 런타임 상태이므로 git 에 올리지 않는다(.gitignore 처리됨).

## 인계

메인 관리자의 사용량이 소진되어 다른 세션에 "일 이어받아"라고 넘길 때는,
`.orchestration/board.md` 와 진행 중인 브리프 파일이 인계 자료다. 인계받는 세션은
**원래 작업의 목적과 금지 사항을 그대로 승계**하며, 작업 성격(점검 → 수정 등)을
임의로 바꾸지 않는다.
